DRY (Don't Repeat Yourself) is a software development principle that emphasizes reducing code duplication by ensuring that a piece of logic exists in only one place. Instead of copying and pasting the same functionality across a codebase, DRY encourages abstraction through functions, modules, or classes to improve maintainability, reduce errors, and make updates easier.

KISS (Keep It Simple, Stupid) stresses that software and system designs should be as simple as possible. Avoiding unnecessary complexity leads to code that is easier to read, understand, debug, and maintain. Overly complicated solutions can introduce more bugs and make collaboration more difficult.

Separation of Concerns (SoC) is the design principle that different aspects of a system should be divided into distinct sections, each handling a specific responsibility. This modular approach improves maintainability, reusability, and scalability by allowing developers to change one part of a system without affecting others. A common example is the MVC (Model-View-Controller) pattern, which separates data handling, user interface, and application logic.

YAGNI (You Ain't Gonna Need It) is a software development principle that advises developers to focus on building only the functionality that is needed right now, rather than adding features or code for potential future requirements that may never arise. The principle emphasizes avoiding over-engineering and unnecessary complexity by steering clear of speculative code. By adhering to YAGNI, developers can deliver simpler, more maintainable systems that are easier to understand, test, and evolve. This approach helps prevent wasted effort, reduces technical debt, and ensures that development is aligned with actual user needs and current project requirements.

# Coupling

**Coupling** refers to the degree of dependence between different components or modules in a software system. It measures how much one module relies on another to function correctly.

* **Tight Coupling** (High Coupling) means that modules are highly dependent on each other, making it harder to change or maintain the system because modifying one module often requires changes in others. This can reduce flexibility and reusability.  
* **Loose Coupling** (Low Coupling) means that modules interact with minimal dependencies, making them more independent. This improves maintainability, testability, and scalability, as changes in one module have little to no impact on others.

Good software design aims for **low coupling** to make systems more modular and adaptable while ensuring that necessary interactions between components remain efficient.

# Cohesion

Cohesion refers to how closely related and focused the responsibilities of a module, class, or function are. A highly cohesive module performs a well-defined task with minimal overlap or dependency on unrelated functionality.

High Cohesion means that a module or class has a clear, single purpose, making the code easier to read, maintain, and reuse. It improves modularity because each component handles a distinct concern.  
Low Cohesion means that a module performs multiple unrelated tasks, leading to a more complex, harder-to-maintain codebase. This often results in tangled dependencies and makes debugging and modifications more difficult.  
Good software design aims for high cohesion while maintaining low coupling to create a system that is both modular and easy to maintain.
